# 河流、城市图标与画布合成（2026-09-08）

本轮承接局内编辑分析，固定此前历史UI优化，仅研究三个renderer owner。保留现有共享工作区改动，无提交或发布。

## 保留：河流同次绘制几何复用

原实现对有描边的可见河流分别生成outline和core几何。现在每次draw中生成一个Path2D，两次stroke共用；仍然先绘制全部outline，再绘制全部core。无outline的河流保持原单次绘制，不建立跨帧缓存。

共享d3 path的context在finally中恢复；绘制上下文也在finally中恢复。不支持Path2D或可切换context时沿用原路径。每次draw重新计算，投影、数据、缩放变化不会读到上次缓存。

目标行为12/12通过；真实TNO原版与新版最终主画布像素一致。实际毫秒见本轮结果报告，不把投影次数减半等同整个河流图层加速50%。

## 保留：城市sprite完整视觉身份与有界复用

移除colorRevision变化时整表清空。缓存键包含准确尺寸、城市级别、首都状态、主题、背景色和实际绘制tokens；同一视觉输入可跨颜色版本复用。使用256项LRU，命中更新使用顺序，避免长期编辑不断积累canvas。

保留背景色和实际tokens，确保主地图改色引发城市对比度改变时得到新sprite。尺寸不再用toFixed(2)合并不同几何。目标行为7/7通过，包括细小尺寸差异、背景及tokens变化、跨revision复用、容量与最近使用淘汰。

256是条目上限，不是浏览器heap或显存的字节上限；尚未证明所有剧本可见组合都不会发生容量抖动。

## 放弃：合成时裁剪overscan源矩形

尝试在identity、source-over、无filter/shadow的上下文中只复制源画布与目标视口交集，其余情形保留原绘制。没有改变图层顺序、建立分组缓存或取消正确失效。

同场使用真实已生成图层、交替旧/候选owner进行暖合成，像素一致，但候选更慢：一会话中位数约5.6→8.3ms，另一会话4.7→7.15ms。已恢复原compositor源码，候选仅保存在.runtime供追溯。暖图层微测量不包含编辑时的图层重绘和新内容提交成本，不可代替整个编辑合成耗时。

首次微测量误包含未激活hgoPreview，requireAll预检返回失败且没有绘制，0.1ms数据无效。修正为已存在的激活pass并断言compose成功后才采信结果。该错误不影响此前独立的真实输入与像素测量。

## 剩余合成问题

此前真实undo CPU profile中的drawImage主要来自最终composeRenderPassesToTarget。暖图层合成微测量较小，不能据此推翻真实编辑profile：新图层内容、资源提交及GPU/CPU同步状态不同。后续若引入分组合成，需要为每个成员建立可靠像素版本、保留层序，并量化额外画布内存；当前证据尚不足以选择具体分组，未加入新的全屏缓存。
